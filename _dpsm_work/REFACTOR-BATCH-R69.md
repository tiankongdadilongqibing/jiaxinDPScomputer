# REFACTOR-BATCH-R69 —— 「调用 ≠ 发动」:时间表把 24 次试触发当成了 24 次发动

日期:2026-10-06。插件 **1.7.19 -> 1.7.20**;`9E66D3EE9D89222896A33BED6AD6B98660C66B324C6218079F8CDC3EF28182AF`(473,600 B)。
起因:用户打完一场正式任务(411001,119.07 s,`result=Lose`)后问「图片里这个技能是做什么的,描述中这个技能应该是
99 秒发动一次」。那个技能是 マッドシーカー 的自动 1 **実験失敗！**,主表冷却 **2970 帧 = 99 游戏秒**,而 R66/R67
的时间表把它印成 `n=24 med=4.97s`。

**结论:用户是对的,页面是错的。** 根因不是抄错数,而是**把「命令被调用」当成了「技能发动」** —— 而且 R66 §②
那条「充能不是发动的闸门」正是从这个错误里读出来的,本轮一并撤回(R65 最早的说法才是对的)。

本轮**不移动任何伤害/归属数值、不改导出形状**(`contribution.schemaVersion` 仍 1.2)。

## 0. 一句话

- **发动 = 调用时技能处于游戏自己的 `Using` 态**;`Charge`/`Usable` 的调用是**试触发**,只计数、不上时间轴、
  不进中位。判据来自 `Skill.GetStatus()`,由 `Policy/SkillActivationPolicy.cs` 承载(未知状态**失败关闭**)。
- **折叠窗口从「固定 0.25 秒」改成「该技能自己的冷却」**:一次发动会在执行窗口内留下**一串** `Using` 调用
  (实测跨度 1.5 / 2.1 / 2.9 / 3.0 / 4.53 秒),0.25 秒的窗口把一次发动切成好几次 —— 这才是 99 秒技能读成 5 秒的机制。
  规则比较(R69 实测,见 §1):9 场语料 342 间隔里 **184 个短于冷却** → 现在 **174 个间隔 0 违规**;
  411001 那场 81 间隔里 **35 个违规** → 现在 **47 个间隔 0 违规**。
- **页面新增 `试N`**,并在汇总行写明「发动 X 条 + 试触发 Y 条(未计入)」;面板 900 → 960 px(行宽 121 → 129)。
  实测渲染那一场:**60 次发动 + 37 次试触发 = 97 条**(`[SKILLTL] SUM cmd=97`);
  マッドシーカー 的行从 `n=24 med=4.97s` 变成 **`99.1  并1条1格 n=1 试23`**。
- **删掉 R66 的记录钩子**(`AddPlayerSkillGameRecord`)与 `rec` 通道:两场(训练场 9999 + 正式任务 411001)
  都是 `rec=0` 且所有跳过计数为 0,即**装上了、一次没被调用**。文件 `Hooks/SkillRecordHooks.cs` 顺带改名
  `Hooks/SkillCommandHooks.cs`(它现在只装 `skl` 那三个入口)。
- 行为用例 **1090 -> 1140**;变异负控 **165 -> 175**;源码 102 -> **104 个 .cs**。

## 1. 规则是怎么定的(两条语料,同一把尺子)

对每一场、每个 (单位, 技能) 分别算:候选 = `status=Using` 的调用;按候选自己的冷却折叠;然后看**相邻两次
发动的间隔是否都 ≥ 该技能冷却**(冷却 = `CoolTimeFrame/30`,即游戏自己印在 `ct=` 上的那个数)。

| 规则 | 9 场语料(471 行) | 411001 那场(97 行) |
|---|---|---|
| A 全部调用 + 固定 0.25 s 窗口(**R66/R67 线上行为**) | 342 间隔 / **184 违规** | 81 间隔 / **35 违规** |
| A2 全部调用 + 按自己冷却折叠 | 182 / 0,但**最大簇跨度 94.47 s** | 49 / 0,最大簇跨度 **94.47 s** |
| B1 仅 `Using` + 固定 0.25 s 窗口 | 193 / **23 违规** | 47 / 0 |
| **B2 仅 `Using` + 按自己冷却折叠(= 本轮)** | **174 / 0** | **47 / 0** |

- **A2 说明「只改折叠」不够**:它确实能让违规归零,但 94.47 秒的那个簇证明**戳点会落在一次充能期的试触发上**
  (マッドシーカー 的第一次调用在 active=0.03 s,真正的发动在 99.07 s)。所以状态判据**必须**有,它管的是
  「戳在哪一刻」;折叠管的是「一次发动只留一格」。
- **B2 的簇跨度全部小于自己的冷却**(最宽 4.53 s 对 10 s 冷却),即「同一技能两次发动不可能快于它自己的冷却」
  这条物理约束在两条语料上都成立 —— 这不是调参调出来的窗口,是约束。
- 冷却读数可靠性:`ct == CoolTimeFrame/30` 在 471 + 97 行里 **0 处不一致**,`ct=0`/`ct=-1` 各 0 行。

## 2. 用户问的那个技能(勘误 + 它是什么)

**勘误**:那一场 マッドシーカー 的自动 1 一共被调用 **25 次** = **2 次 `Using`**(都在 active=**99.07 s**,
同一瞬间的重复上报,被 99 秒冷却折成一格)+ **23 次 `Charge`**(`wait` 一路从 2942 降到 0)。真正的发动 **1 次**,
发生在 `active=99.07 s` —— 她的计数器也在 `active=101.17 s` 走满 2970 帧后归零重置。**与描述一致。**

**技能是什么**(主表 `auto_skill` id 56):台词「得たものがあれば失敗ではないさ。」;`minFirstCoolTime =
minCoolTime = maxCoolTime = 2970`(99 游戏秒,满级同值);`durationTime = -1`、`stock = 0`;
天赋只有 **1039「播放攻击」** 与 **1092「AttackDataForceUpdate」** —— 没有伤害/增益/治疗天赋。即:**它是
「播放一次攻击 + 刷新攻击数据」的容器**,伤害来自她自己的攻击。参考:她那一场的奥义「犠牲による応用力」
(槽 10,`type=2(OverSkill)`,自己 3 秒冷却)发动 24 次、中位 4.97 s —— **约 5 秒是她的行动节奏**,两个技能都挂在
这个节奏上,区别只是自动技能的 99 秒冷却只放行一次。

## 5. 覆盖不到的

1. **`Using` 只是必要条件,不是充分条件的证明**:两条语料上「仅 Using + 按冷却折叠」0 违规,说明它与
   「同一技能不可能快于自己的冷却」这条物理约束**相容**;但它并不排除「一次执行里第一次调用之前还有一次
   `Using` 调用」这类边界(那会被折叠吃掉,不会多打一格)。
2. **`[SKILLTL] skl`(奥义)那一路的冷却折叠没有用实机数据核过**:R68 那场的 `skl` 行没打 `ct=`,所以离线只能核
   `cmd` 那一路。下一场的 SUM 会带 `tries=`/`unclassified=`,奥义行也会按各自的冷却折叠。
3. 探针、钩子与渲染仍不在 BehaviorTests 的编译清单里(需要 IL2CPP/Unity 面)。
4. **`Skill.ActivationType` 仍无解释力**:R66 §2b 把希望寄托在它上面,实测每一个单位每一个技能都是 `act=0 actP=0`
   (与主表 `activationType=0` 一致)。本轮不再引用它作为触发条件的答案。
