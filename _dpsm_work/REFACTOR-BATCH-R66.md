## 2. R65 的答案里,有三处要改(先认,再改)

### 2a. `minCoolTime`/`maxCoolTime` 是**技能等级区间**,不是同一等级的两个槽

R63 错在把主表当秒(已由 R65 删掉),R65 又把这一对读成「同等级下的 min/max」并留下悬案
「T.O.W.E.R.typeR 同一槽一会儿 420 一会儿 300」。**9 场语料给出的答案是等级**:

    トレイラ 300/240  ->  L2 = 270,  L3 = 240   (每级 -30)
    ソフィー 420/300  ->  L1 = 420,  L3 = 300
    ポポロット 270/210 ->  L1 = 270,  L3 = 210

即 **`CoolTimeFrame` = 按技能等级在 min(L1) 与 max(满级) 之间取值**,5 个单位 × 2 个等级共 10 个观测点全部
落在这一规则上;`level=3` 是本内容里的满级(所有满级单位的行都是 3)。

R65 §3a 那 4 行 420 的原始行仍在本仓库(`tests/_r64_live_autosk.tmp.txt`,03:30:03–03:30:14),它们带着
`level=1` 而同一场的 `chg` 行带着 `level=3` —— 所以那**不是**「同槽换技能」的谜,而是**同一单位同一技能的两个
等级对象同时可达**(R64 那场 T.O.W.E.R 正处于升级过程中)。R65 据此改的身份键(R65 §3a 第 3 条)方向是对的,
理由当时写错了;**R66 给身份键再加对象标签 `inst=`**,把「同名同 id 的两个对象」从"看起来自相矛盾的一行"变成
"两行各说各话"。

### 2b. **充能不是发动的闸门**(R65 的核心结论要撤回)

R65 的答案(已发给用户)是:「充能 240 = 8.0 游戏秒,充满后停 `Usable` 等**下一次普攻**才打出去,所以间隔
> 充能」。9 场 471 行不支持它作为通则:

- **157/471 次发动发生在 `Charge`**(没充满),其中 `マッドシーカー` 的 `wait` 读数是 2870 → 2721 → 2572 →
  2423(`charge` 一路在降),而它的 `CoolTimeFrame` 是 **2970(=99 游戏秒)**,实测中位间隔却只有 **4.97 秒**;
- 至少 6 个单位的中位间隔**短于**自己的充能:マッドシーカー 4.97 vs 99.0、ソフィー 4.30 vs 14.0、
  T.O.W.E.R.typeR 4.53 vs 10.0、レヴナント 3.93 vs 5.0、ルーチェルト 2.50 vs 5.0、メアリー 10.10 vs 13.0。

所以正确的说法是:**`WaitCountFrame`/`CoolTimeFrame` 是给玩家看的资源条,不是发动的判定**。那么「什么触发它」
就得读游戏自己的字段 —— R66 已把 `Skill.ActivationType`/`ActivationTypeParam` 打进行(`act=`/`actP=`)。
**这是一个被摆到数据面前的问句,不是一个结论**:下一场日志的 `act=` 列才是答案(见 §5)。

### 2c. トレイラ 的间隔:3 个样本 → 47 个样本

| | R65(1 场,3 次发动) | R66(9 场,47 个间隔) |
|---|---|---|
| 间隔 | 15.20 / 12.03 游戏秒 | min 0.20 / p25 6.60 / **中位 9.00** / p75 13.13 / max 13.50 |

R65 那两个数是**同一分布的高位**,不是规律。**中位 9.00 游戏秒**才是「暗沌への導き」的常态
(它的充能是 8.00 游戏秒 —— 巧合地接近,但 §2b 说明这个接近不能推而广之)。
另外:**时钟**上,9 场数据里 `active`(战斗钟)会**停**(实测 `wait` 维持 186/240 达 6 个真实秒而 `active` 一动不动,
`wall` 照走),所以间隔只能在**战斗钟**上量;`dActive` 紧而 `dWall` 散(イグナ 22 个间隔:
`dActive` 7.57–7.80,`dWall` 5.17–27.41)正是这个原因。

## 5. 覆盖不到的(必须写下来)

1. **`AddPlayerSkillGameRecord` 是否等于"发动时刻"仍未证实**。静态上无法问(interop 只有调用桩),所以:
   页面上**打印两条通道各多少条**,空态直接写「本场尚未观测到我方技能发动」,`rec=0` 时额外警告
   「奥义/特殊技能只能由它观测」,并且每次记录都写 `[SKILLTL] rec …` 行。**下一场日志直接回答它**;
   在那之前,奥义一列要读成"已观测",不能读成"完整"。
2. **`SkillTimelineProbe.cs` / `SkillRecordHooks.cs` / `AutoSkillProbe.cs` / 页面渲染不在 BehaviorTests 的
   编译清单里**(需要 IL2CPP/Unity 面),所以本轮这些代码**没有行为测试**;被覆盖的是纯规则、页面文本,
   以及"成员名正确"这个由编译器保证的性质。
3. **时间表按(单位,技能,类型)合并,不按技能等级拆行**。§2a 说明同一个技能可能同时有两个等级对象
   (充能不同),它们在表里会并成一行。等级/充能/对象标签的证据在 `[AUTOSK]` 行里(`level=`/`inst=`/`ct=`),
   要追那件事请读那一侧。这是**有意的**:时间表回答"什么时候发动",不是"当时冷却多少"。
4. **`rec` 通道的形状未知**:`eUserRecordType` 里 Start/Finish 成对存在,本轮只收四种 `*Start`
   (`OverSkillStart`/`SpecialSkillStart`/`AutoSkill1…`/`AutoSkill2…Start`),其余(含攻击、屏幕手势、
   状态/增益记录,它们共用同一个 sink)计入 `nonStart` 计数。若下一场 `nonStart` 巨大而 `rec=0`,
   说明该 sink 的 Start 分支走了别的路。
5. **`gameIdx` 的语义仍未定死**:`0` 与 `1` 在 9 场里都指向同一技能身份(79/79 的 `n=` 证据),
   但"`1` 是 1 基槽位还是 0 基被动位"要等 `[AUTOSK] cmdidx` 的 `named=`/`rosterPos=` 两列。
   这是**上一轮就开着的问题**,本轮把它从"猜"变成"打印出来"。
6. 本轮**没有**动 `contribution`/导出形状(仍 1.2),也没有动伤害/归属的任何一个数。
