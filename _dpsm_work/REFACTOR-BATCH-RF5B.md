## 1. 迁了什么

| 成员 | 作用 |
|---|---|
| `DispWidth(char)` / `DispWidth(string)` | 显示列宽:CJK 一字符两列 |
| `Cell(string)` | 进入定宽列前的规范化(把 U+00D7 换成 ASCII `x`;普查过全部导出名,只此一个字形宽度随字体变) |
| `PadR` / `PadL` | 按显示列补空格;**永不收缩** |
| `Num(long)` / `Fmt(double)` / `Pct(double)` | 千分位 / `:N0`(NaN 与 Inf 归零)/ 百分比两位 |
| `Amt(double, int)` | 金额列:能放下就完整打印,放不下退到 M/G/T 后缀,**绝不静默截断数字** |
| `CutMark` + `Fit(string, int)` | 按显示列截断,尾部 `..`;**绝不切断代理对** |

这些成员原来在 `Ui/OverlayUGUI.Rows.cs` 里,而那个文件同时拥有 uGUI 池、行模型与贡献视图。
它们**不含任何 Unity 类型**(只用 string/int/double/Math),这正是方案要求它们单独成层的理由:
现在的行为套件**编译并直接执行生产实现**,而不是靠一份 Python 副本推断。

## 2. 方案要求的用例类别(全部有固定期望)

| 类别 | 用例 |
|---|---|
| **CJK** | `DispWidth("角色")==4`、混合 `"abc角色"==7`、全角数字 `"１２３"==6`、半角片假名 `"ｱ"==1`(故意不算宽)、全角拉丁 `"Ａ"==2` |
| **长名** | `Fit("あああああ", 6)=="ああ.."`、`Fit("abcdefghij", 6)=="abcd.."`、以及 6 组语料 × 0..20 预算的扫描:结果宽度**从不超过预算** |
| **极值** | 语料最大值 `Amt(2.1e8, 11)` 恰好 11 列(`"210,000,000"`);`Amt(1e9, 11)` 退到 `"    1000.0M"` 并仍恰好 11 列 |
| **零** | `Num(0)=="0"`、`Fit(s, 0)==""`、`PadR("",3)=="   "` |
| **未知** | `Cell(null)==""`、`Fmt(double.NaN)=="0"`、`Fmt(+Inf)=="0"`、`Pct(NaN)=="0.00%"`、`Amt(NaN,6)=="     0"` |
| **代理对** | 星面 CJK 字宽 2(`"U00029E3D"` 两个 UTF-16 单元各宽 1);`Fit` 在预算 3 时返回 `".."` 而**不是**半个代理;并断言任何预算下输出都不含孤立代理 |

## 3. 布局守卫现在做什么、不做什么(澄清一件长期含糊的事)

读代码后的结论(原文写在 [check_contribution_layout.py](<check_contribution_layout.py>)):

| 它做 | 它不做 |
|---|---|
| 解析 `OverlayUGUI.Rows.cs` 里**列标签与列宽**(`PadR("角色", 16)` …)与 Python 副本逐项对账 | **从不**把 C# 的 `DispWidth`/`PadL`/`Fit` **函数**与 Python 副本对比 |
| 用自己的副本重放 842 行导出文本的可见列宽(artifact 侧差分) | 不执行 C# 实现 |
| `--selftest` 用 1.7.6 语义反证自身有牙(旧 Fit → 32 文件 315 违规) | — |

也就是说:列宽有双重来源校验,而**宽度/截断算法此前只有一份 Python 副本** + 导出数据的间接验证。
本轮把这半边补上:算法现在是**编译进测试工程、被 43 个用例直接执行的生产代码**。
守卫为什么仍然全绿:它解析的列标签/宽度都还在 `Rows.cs` 里(本轮只搬走了算法)。
