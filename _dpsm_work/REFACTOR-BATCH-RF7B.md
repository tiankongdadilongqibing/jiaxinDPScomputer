## 1. 判定的证据是什么

对每个未判定脚本,机械地算三件事:

1. **流水线是否运行它**(n0 的 argv 里出现);
2. **是否有别的脚本导入它**(从 RF7a 的 `imports_local` 图谱反查被导者);
3. **当前文档集是否点名它**(PROJECT-STATUS / HANDOFF / REPO-BOUNDARY / 文档索引)。

三者全否 ⇒ `status: "indexed"`,`evidence` 写成这条可复核的事实:
"no pipeline entry, nobody imports it, and the current document set never names it"。
本条**不删除任何脚本**(方案要求 R0 的归档只做索引)。

**一个自指的坑**:第一版把 `TOOL-REGISTRY.md` 也当"文档集"来查,于是**零条**能通过——因为那份报告由注册表生成,
必然列出每个脚本名。这是"用输出验证输入"的循环,已从证据来源里剔除并在注释中写明。

## 2. 守卫的 G 检查:判定必须可被复核

`indexed` 的语义是"没有活的东西依赖它"。守卫现在自己算一遍:

| 条件 | 违反时 |
|---|---|
| 它 `in_pipeline` 或在流水线 argv 里 | `G marked indexed but the pipeline runs it` |
| 有任何脚本 `imports_local` 指向它 | `G marked indexed but another script imports it` |

所以"标成 indexed"不是一次性动作:一旦有人开始导入它、或把它接进流水线,构建立刻变红。
剩下 31 条**故意不判定**——它们被引用,判定它们需要读代码判断"这个引用还算不算活",那正是下一批的事。
