## 1. 加了什么

| 成员 | 作用 |
|---|---|
| `ColumnSpec { Label, Width, Right }` | 一列的标签、显示列宽、补空方向 |
| `ContributionColumns.T1/T2/T3` | 三张表的列定义(共 20 列) |
| `T1LineWidth`/`T2LineWidth`/`T3LineWidth` | **行**宽 = 列宽之和 + 2(前导两空格) |
| `WidthOf(cols)` | 列宽之和(不含前导空格) |
| `HeaderLine(cols)` | 表头行:两空格 + 每列按其对齐方向补到自己的宽度 |
| `T1TotalsLine(...)` | T1 合计行:标签 + 四个份额列求和,两个占比列留空 |

渲染器里原来手写的三行表头与一行合计,现在都是**一行调用**。

## 2. 一个必须实测才敢写下来的语义

我最初把 `T1Width` 写成 85(以为列宽之和就是 85),测试立刻给出 83 —— 真实语义是:

| 量 | 值 |
|---|---|
| T1 列宽之和 | **83**(16+11+8+11+11+11+9+6) |
| T1 **行**宽 | **85**(两前导空格 + 83)= 布局守卫与导出里那个"85 列" |
| T2 | 列 75 / 行 **77** |
| T3 | 列 51 / 行 **53** |

这正是"固定期望输出"的价值:它把我猜错的地方立刻变成了红灯,而不是把一个含义模糊的常量留在代码里。
常量的语义现在写在注释里,用例同时钉住"列和"与"行宽"。

## 3. 单一来源到什么程度(诚实说)

| 位置 | 现状 |
|---|---|
| 表头(3 行) | ✅ **由定义构造**,不可能与定义不一致 |
| T1 合计行 | ✅ 由定义构造 |
| 数据行(3 张表) | ⚠️ 仍内联宽度:它们把 `Amt` 的 M/G/T 回退与列交错在一起,逐列迭代会改动**热渲染路径**;本轮不为了整齐去动它 |
| 数据行与定义的一致性 | ✅ **由布局守卫对账**:守卫解析定义里的标签/宽度,再解析渲染器 T1 数据行的宽度序列,两者不等就是红灯(篡改定义常量也会红) |

所以"单一来源"目前是:**定义是唯一声明处,数据行是受校验的副本**。把副本也消掉,需要先有渲染层的行模型(§6)。

两次都是它把"我以为对"的东西变成了红字。
