# 报告:未识别规则种类(unknown_kind)的定位(R52)

> 目的:把"贡献账残差里那个 4.33% 到底是什么"从一句话结论变成**可复现、可证伪**的定位。
> 输入:_dpsm_work/attribution_census.py 对**部署构建**跑出的那场导出逐折叠重算。
> 本报告**没有改动**任何归属规则;第 4 节给出的是**候选**路径与它需要的决定。

## 0. 一句话

**它不是"未知的种类",而是一条已知的规则(刻印 id=26 赋予的 `被伤害+10%`)缺了"谁给的"**。
本场 5,862 个未归因折叠 **全部** 属于 `kind="given"`,来源只有 4 个 origin,全部是 `given#4..7/1006/-10`,
因子恒为 `1.1`,受击方只有 ショゴス;而规则持有者在可读的名册里**唯一**:`エヴァラス・フラウ(key=9)`,
且携带**两份**同名刻印 —— 正是文档里那句"两个副本 = ×1.10²"。

自述与重算完全一致(合计 35,961 折叠 = 导出的 `foldAccounting.total`;5,490 个可分析命中中 5,488 个带折叠):

| ability_holder_unique | 6,003 | 29,978,086.42 |
| **unknown_kind** | **5,862** | **8,375,105.67** |

`unknown_kind` 的**全部 4 行明细**:

| origin | 因子 | 折叠 | 金额 | 受击方 | 时间窗 |
|---|---|---|---|---|---|
| `given#6/1006/-10` | 1.1 | 1,839 | 2,531,919.02 | ショゴス(76 个实例) | 19.60–118.47 |

| `given#4/1006/-10` | 1.1 | 1,092 | 1,655,633.81 | ショゴス(69 个实例) | 5.10–91.60 |
| `given#5/1006/-10` | 1.1 | 1,092 | 1,655,633.81 | ショゴス(69 个实例) | 5.10–91.60 |

四条明细的 label 只有一个:**`被伤害+10%(赋予)`**。也就是说 4.33% 的伤害来自**一条**规则的两个副本,
不是"很多没见过的种类"。占折叠 16.3% 而只占伤害 4.33%,是因为它的份额小(每击只有 ln1.1/lnM)。

## 3. 为什么"没人认领":given 通道的健康度(导出自带的反证)

导出的两段自检数字直接把原因钉死:

| 计数器 | 值 | 含义 |
|---|---|---|
| `rosterAudit.giveApplied` | 5,946 | 真正折进链、并写下 `kind="given"` 折叠的条目数 |
| `rosterAudit.giveCancelled` | 24,323 | 被全局规则通道吸收的条目(主要是 `1006/-15`) |
| `rosterAudit.giverResolved` | **0** | 全场**没有一次**成功认出授予者 |
| `rosterAudit.giverNull` | 30,269 | 查表未命中次数(= 5,946 + 24,323,口径对得上) |
| `rosterAudit.giverErrors` | 0 | 不是读字段抛异常,是**表里没有** |
| `givenApplies.hookCalls` | `{"addTalent": 12}` | 授予类 `ActExecute` 一整场只响了 12 次 |
| `givenApplies.nullGuest` | **12** | 12 次里 guest 参数**全部读不出来** |
| `givenApplies.targets` | **0** | 于是"目标 → 最近授予者"这张表**是空的** |
| `givenApplies.lookupHits / lookupMisses` | 0 / 34,688 | 34,688 次查询 **0 命中** |

两条结构性事实:

1. **缺的不是种类,是身份。** `FoldStep.Kind` 全场只有 6 个值(`text` / `talent` / `global` / `given` /
   `madness` / `atkadd`),前三个走各自的分支,`atkadd` 一定带 `byUnit`,所以**只有 `given` 与 `madness`
   这两个"靠 byUnit 认人"的通道可能落进 `unknown_kind`**。本场 `madness` 折叠 869 个**全部**带 byUnit
   (自施加回退),`given` 折叠 5,946 个**一个都没有** —— 于是 100% 的 `unknown_kind` 来自 `given`。
2. **同一套钩子,两个探针的处理不对称。** `StatusApplierProbe.Note` 在 guest 读不出来时把它**记为自施加**
   (`_lastApplier[o] = o`,有 5 场数据与用户确认支撑),所以 madness 折叠能认到人;`GiveApplierProbe.Note`
   在 guest 读不出来时**什么都不记**(`if (g != null)`),同一现象在 given 通道就变成了空表。
   这不是"规则种类未知",这是一处**可指名的实现不对称**。
3. 就算 guest 可读,12 条记录也覆盖不了 34,688 次查询:钩子只在"施加动作执行"的那一刻响,而条目在整场里持续参与折叠
   (本场 5,946 个条目分布在 2,973 个命中上)。所以"最近授予者表"这条路**容量上就不够**,不是调参能救的。

## 4. 可判定的候选路径(推断;**未改任何分数**)

刻印 id=26 的主数据文本与名册里的素质表给了**第三条路**:不看运行时,看**谁持有这条规则**。

| 证据 | 值 |
|---|---|
| 规则文本 | `ブロックしている敵の被ダメージ+10%（前衛のみ）`(id=26,slot=**刻印**) |
| 素质表 | `type=1006 p=[-10,0,0] cond=GiveTalent(1) timing=Block` |
| 折叠 origin | `given#<i>/1006/-10` —— **同一个 (type,param)** |
| 名册持有者 | 我方 team=1 中持有 id=26 的只有 **1 个**:`エヴァラス・フラウ(key=9)`,且**两份**(表里出现两次) |
| 候选判定 | `unique (1 candidate)` —— 4 行明细全部如此 |

于是本场 5,862 个折叠的提供者**是唯一确定的**。这条路径是**推断**(持有 ≠ 此刻正在阻挡该敌人),
所以它必须像 `atkadd` 那样**分开计理由、分开算歧义**,绝不静默猜:

* 唯一持有者 → 建议理由码 `given_carrier_unique`;
* 多个持有者 → `given_carrier_ambiguous`(**仍然不归因**);
* 一个都没有 → `given_carrier_none`。

**本报告到此为止:是否把这条规则接进归属,是一个会移动单位之间信用的决定(并需要离线核对器同步实现),
留给你决定。** 本轮只把它做成"提取流程"的一部分:证据包会把候选判定算好,而不是让下一个人再写一次性脚本。

## 6. 尚缺的东西(诚实清单)

* 本报告**没有**证明"刻印 26 的持有者一定在那一瞬间阻挡了该敌人",只证明了持有者唯一;
* `given#i` 里的 `i` 是该受击方 `m_giveTalentData` 列表的下标,本报告用它区分副本,没有用它反查来源;
* `gd.ownerAction` 字段读取这条路在 1.5.4 已被判死(每个条目都抛异常),本轮**没有**重试;
* 真实"谁给的"最终仍需一条可读的运行时证据;提取流程(R52 轮)负责把这类证据一次性收齐。

## 8. 第三场:机制被确认,但暴露出**第二种、更糟的失败模式**(R53)

> 用户于 2026-10-05 13:55 又打了一场(导出 `battle_411001_20261005_135533.json`,13,361,418 字节,118.57 s),并问:这场同样有两个「阻挡增伤」,为什么**没有**未归因伤害?
> 答案:因为「谁给的」这条路这次**填上了表** —— 但它填的是**别人**。

### 8.1 三场并排:同一个探针,两种结局

| 项 | 第一场 08:25 | 第二场 13:25 | 第三场 13:55 |
|---|---|---|---|
| 授予条目(已折进链) | 5,946 | 5,856 | 5,360 |
| 钩子调用 | 12 | 11 | **222** |
| 其中 guest 读不出 | 12 | 11 | **42** |
| 表里的目标数 | **0** | **0** | **1** |
| 查表命中/未命中 | 0 / 34,688 | 0 / 34,964 | **9,924 / 0** |
| `giverResolved / giverNull` | 0 / 30,269 | 0 / 31,021 | **8,369 / 0** |
| `unknown_kind` 折叠 | 5,862 | 5,774 | **0** |
| `creditedShare` | 0.95671 | 0.958009 | **1.0** |

**机制因此被确认**(§3 的预测):表空 → 残差落在 `unknown_kind`;表被填 → 这同一条规则的折叠全部被认领,残差消失。重算与自述三场都 MATCH。

### 8.2 但第三场认领给了一个「不可能给它」的单位

第三场的 `contribution.rules` 里:

    ruleName=被伤害+10%(赋予)  kind=given  side=vic  ownerName=イグナ  hits=2,645  folds=5,320  damageEquivalent=6,705,889.97

而同一场导出的名册里,`1006/-10`(刻印 id=26「ブロックしている敵の被ダメージ+10%」)的持有者是 **エヴァラス・フラウ(两份)与 チェイシィ(两份)** ——`イグナ` 的**全部 13 项能力**里只有**一个** GiveTalent 通道:`80/5`(神器 id=10120 バルザイの偃月刀,cond=GiveTalent(1))。
**イグナ 没有任何能授予 `1006/-10` 的能力。**

原因在源码里是可直接读出来的:`GiveApplierProbe` 的表**只按目标名做键**( `_giver[guest] = owner`,写入处 `if (g != null)` );
而折叠侧问的是 `LastGiver(Aggregator.NameOf(bo))` —— `bo` 就是受击方。**键里没有「授予了什么」。**
所以问句实际是:「谁最近给 ショゴス 授予过**任意**东西?」,答案被当成「谁给了 ショゴス 被伤害+10%」。
第三场 180 条记录全是 (`owner=イグナ, guest=ショゴス`),横跨 t=0.1…117.67,于是整场每一个 `-10` 折叠都拿到 `byUnit=イグナ`(`given10_byUnit = {イグナ: 5360}`)。

**结论:第三场「没有未归因」不是数据变好,而是一个自信的错答。** 前两场的 4.2–4.3% 残差,是同一处缺口的**诚实形态**;第三场把它换成了 6,705,889.97 的错误归属。

### 8.3 诚实的边界

* 名册证据是直接的(`イグナ` 自己的 13 项能力里没有 `1006/-10`);我另外扫了一遍主数据表想找「全游戏还有谁能授予 `1006/-10`」,但我的访问器没对上转储的表结构(**0 命中**),所以那一扫**不构成证据**,只能算未完成。
* 本场的 `1006/-10` 有**两个**持有者,所以即便用 §4 的「唯一持有者」规则,这场也只会得到 `ambiguous`(仍然不归因)—— 而运行时那条路给了唯一一个名字。两条路在真相两侧各错一边:**诚实的答案是「不归因 + 两个具名候选」**。
* 名义上的边界:这次只有 1 个目标表项、1 个写表者,所以错得很干净;多个单位都给同一目标授予过东西时,表里只留最后一个。

### 8.4 建议的修法(会移动信用,**需要你决定**)

1. **按 (目标, type/param) 做键**:钩子是 POSTFIX(授予条目此刻已经存在),所以在 `Note` 里读一下 **guest 自己**的 `m_giveTalentData` 最新条目,把 `type/param` 一起记进键;折叠侧用 `given#i/<type>/<param>` **精确查**。
2. **精确匹配才归因**;旧的「只按目标」那条路**只计数、不再用于给信用**(它已被证明答的是另一个问题)。计数要分开(`searched_exact / matched_exact / targetOnlyRejected`),不能糊成一个数。
3. 预期效果:第一、二场**不变**(仍然是 4.2% 的诚实残差);第三场那 6,705,889.97 回到未归因,除非精确键真的命中 —— 按现有记录,エヴァラス/チェイシィ 的刻印-26 授予从未让钩子带上可读的 guest,所以它大概仍会是不归因(由 §4 的候选判定把两个持有者列出来)。

也就是说:这条修改的方向是**撤销一个没有证据支持的归属**,而不是增加归属;但它确实会改变游戏内 KDA 数字,所以照例由你拍板。
