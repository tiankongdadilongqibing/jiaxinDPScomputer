# 报告:未识别规则种类(unknown_kind)的定位(R52)

> 目的:把"贡献账残差里那个 4.33% 到底是什么"从一句话结论变成**可复现、可证伪**的定位。
> 输入:_dpsm_work/attribution_census.py 对**部署构建**跑出的那场导出逐折叠重算。
> 本报告**没有改动**任何归属规则;第 4 节给出的是**候选**路径与它需要的决定。

## 0. 一句话

**它不是"未知的种类",而是一条已知的规则(刻印 id=26 赋予的 `被伤害+10%`)缺了"谁给的"**。
本场 5,862 个未归因折叠 **全部** 属于 `kind="given"`,来源只有 4 个 origin,全部是 `given#4..7/1006/-10`,
因子恒为 `1.1`,受击方只有 ショゴス;而规则持有者在可读的名册里**唯一**:`エヴァラス・フラウ(key=9)`,
且携带**两份**同名刻印 —— 正是文档里那句"两个副本 = ×1.10²"。

## 3. 为什么"没人认领":given 通道的健康度(导出自带的反证)

导出的两段自检数字直接把原因钉死:

| 计数器 | 值 | 含义 |
|---|---|---|
| `rosterAudit.giveApplied` | 5,946 | 真正折进链、并写下 `kind="given"` 折叠的条目数 |
| `rosterAudit.giveCancelled` | 24,323 | 被全局规则通道吸收的条目(主要是 `1006/-15`) |
| `rosterAudit.giverResolved` | **0** | 全场**没有一次**成功认出授予者 |
| `rosterAudit.giverNull` | 30,269 | 查表未命中次数(= 5,946 + 24,323,口径对得上) |
| `rosterAudit.giverErrors` | 0 | 不是读字段抛异常,是**表里没有** |
| `givenApplies.hookCalls` | `{"addTalent": 12}` | 授予类 `ActExecute` 一整场只响了 12 次 |
| `givenApplies.nullGuest` | **12** | 12 次里 guest 参数**全部读不出来** |
| `givenApplies.targets` | **0** | 于是"目标 → 最近授予者"这张表**是空的** |
| `givenApplies.lookupHits / lookupMisses` | 0 / 34,688 | 34,688 次查询 **0 命中** |

两条结构性事实:

1. **缺的不是种类,是身份。** `FoldStep.Kind` 全场只有 6 个值(`text` / `talent` / `global` / `given` /
   `madness` / `atkadd`),前三个走各自的分支,`atkadd` 一定带 `byUnit`,所以**只有 `given` 与 `madness`
   这两个"靠 byUnit 认人"的通道可能落进 `unknown_kind`**。本场 `madness` 折叠 869 个**全部**带 byUnit
   (自施加回退),`given` 折叠 5,946 个**一个都没有** —— 于是 100% 的 `unknown_kind` 来自 `given`。
2. **同一套钩子,两个探针的处理不对称。** `StatusApplierProbe.Note` 在 guest 读不出来时把它**记为自施加**
   (`_lastApplier[o] = o`,有 5 场数据与用户确认支撑),所以 madness 折叠能认到人;`GiveApplierProbe.Note`
   在 guest 读不出来时**什么都不记**(`if (g != null)`),同一现象在 given 通道就变成了空表。
   这不是"规则种类未知",这是一处**可指名的实现不对称**。
3. 就算 guest 可读,12 条记录也覆盖不了 34,688 次查询:钩子只在"施加动作执行"的那一刻响,而条目在整场里持续参与折叠
   (本场 5,946 个条目分布在 2,973 个命中上)。所以"最近授予者表"这条路**容量上就不够**,不是调参能救的。

## 4. 可判定的候选路径(推断;**未改任何分数**)

刻印 id=26 的主数据文本与名册里的素质表给了**第三条路**:不看运行时,看**谁持有这条规则**。

| 证据 | 值 |
|---|---|
| 规则文本 | `ブロックしている敵の被ダメージ+10%（前衛のみ）`(id=26,slot=**刻印**) |
| 素质表 | `type=1006 p=[-10,0,0] cond=GiveTalent(1) timing=Block` |
| 折叠 origin | `given#<i>/1006/-10` —— **同一个 (type,param)** |
| 名册持有者 | 我方 team=1 中持有 id=26 的只有 **1 个**:`エヴァラス・フラウ(key=9)`,且**两份**(表里出现两次) |
| 候选判定 | `unique (1 candidate)` —— 4 行明细全部如此 |

于是本场 5,862 个折叠的提供者**是唯一确定的**。这条路径是**推断**(持有 ≠ 此刻正在阻挡该敌人),
所以它必须像 `atkadd` 那样**分开计理由、分开算歧义**,绝不静默猜:

* 唯一持有者 → 建议理由码 `given_carrier_unique`;
* 多个持有者 → `given_carrier_ambiguous`(**仍然不归因**);
* 一个都没有 → `given_carrier_none`。

**本报告到此为止:是否把这条规则接进归属,是一个会移动单位之间信用的决定(并需要离线核对器同步实现),
留给你决定。** 本轮只把它做成"提取流程"的一部分:证据包会把候选判定算好,而不是让下一个人再写一次性脚本。

## 6. 尚缺的东西(诚实清单)

* 本报告**没有**证明"刻印 26 的持有者一定在那一瞬间阻挡了该敌人",只证明了持有者唯一;
* `given#i` 里的 `i` 是该受击方 `m_giveTalentData` 列表的下标,本报告用它区分副本,没有用它反查来源;
* `gd.ownerAction` 字段读取这条路在 1.5.4 已被判死(每个条目都抛异常),本轮**没有**重试;
* 真实"谁给的"最终仍需一条可读的运行时证据;提取流程(R52 轮)负责把这类证据一次性收齐。
