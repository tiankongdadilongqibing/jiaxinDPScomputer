## 1. 为什么"判据"是这一族最值得先搬的部分

`RegisterGlobalDebuffs` 里有一段**日文子串门链**,决定"这条能力分句算不算战场级规则、是哪种形状"。
它决定了两条真实规则的行为,却在一次 IL2CPP 对象遍历的里面 —— 只能靠打仗测。搬出来之后:

| 判据 | 位置 | 例子 |
|---|---|---|
| 形状门 | `Classify` | 必须含 `被ダメージ`,或同时含 `与ダメージ` 与 `味方` |
| 战场级门 | `Classify` | 敌方受伤型必须说 `全て`/`すべて` **且**点名 `敵`/`相手`/`対象`;`ブロック` 不算 |
| 局部保留门 | `Classify` | 任何含 `耐久`/`HP` 的分句都留在逐击扫描里(那里才知道当前耐久) |
| 因子门 | `Classify` | 解析出的倍率是 1.0 ⇒ 不是规则 |
| 形状字段 | `Classify` | `それぞれ` ⇒ 逐状态;`魔法`/`物理` ⇒ 限定;`前衛`/`後衛` ⇒ 位置 |
| 登记跳过 | `SkipRescan` | 同名 ⇒ 已扫过;空条目 + 名字备忘同名 ⇒ 已扫过;名字不同 ⇒ **指针被复用,必须重扫** |
| 阀门 | `ShouldReclaim` / `ShouldClearAll` | 400 触发回收,回收后仍 > 600 才整表清空(表**从不**在战斗结束时清) |

## 3. 行为保持

1. **门链逐行搬运**:比较符号、短路顺序、`IndexOf`/`Contains`/`StringComparison.Ordinal` 全部不变;
2. **副作用不变**:因子解析仍在探针(`ParseDamageModifier`),策略通过回调请求它 —— 用例额外钉住"**被拒的分句根本不会去解析因子**";
3. **原生读取不动**:能力列表、文本、指针、`bo.Name`、`data.Name` 仍在探针;记录的 `Owner`/`OwnerObj`/`OwnerName`/`Source` 由探针填;
4. **阀门两级语义保留**:第二级判的是**回收之后**的计数(用例 `the-second-test-runs-on-the-post-reclaim-count` 把这点写下来);
5. **登记跳过的四种情形**各自有用例,包括"空条目 + 名字备忘"这条容易被误读的 memo 语义。

## 4. 未做(诚实清单)

1. **注册表状态**仍在 `CompositionProbe._globalRules` / `_ruleOwnerName`:本轮只动了判据,没有动所有权 —— 矩阵 §7 的前置(时序用例)仍然缺;
2. **"注册早于结算"的时序用例**需要能把注册路径驱动成事件,即需要 IL2CPP 侧的 `BattleObject`/`BuffBase` 桩;代价高,且桩本身容易失真;
3. **`ApplyGlobalDebuffs`(应用侧)**的判定未动(它以 `FoldContext` 为输出、读受害者状态),属同一族的另一半;
4. 因子解析(`ParseDamageModifier`)本轮未覆盖:它没有被修改,且真实导出数据在间接验证它。
