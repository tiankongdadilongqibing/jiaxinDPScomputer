## 1. 错误本身,以及它证明了什么

按"只有 `imports_local` 才算依赖"来算,**`n0_acceptance.py` 看起来是死的**——因为没人 `import` 它。
可它是整个验收的**入口**(`python n0_acceptance.py`),它**按名字**调用其它工具(`subprocess`)。
同理 `tests/negative_control.py`(每轮的变异负控)、`tests/il_equiv.py` 等。

**结论**:在这个仓库里,**"谁 import 谁"不足以判定存活**;**按名字调用**才是主要的使用方式。
所以"传递性活跃"这个机械判据**不够**,除非注册表里补上"谁按名字调用我"这一栏(它现在没有)。

处置:**只还原 `tool_registry.json`**(回到 23 活跃 / 28 未判定 / 上限 28),**保留** G 的放宽与两个对照,
因为放宽让"死子树"在**原理上**可判——只是**数据模型还不够**。

## 2. 于是本轮真正的产物:J

`J` 把这次错误变成一道**能报警的规则**:被标为 `indexed` 的脚本,**不得**出现在
`n0_acceptance.py` 的文本里。当前数据下它**不触发**(45 条已索引里没有一条被 n0 点名),
所以它是**预防性**的——但正是它会在下次"按名字调用"的脚本被误判时立刻变红。

## 3. 余下 28 条要怎么才真的能判

需要的不是更强的闭包,而是**更全的依赖信息**:
1. 给注册表加一栏 `invoked_by`(谁按名字/shell 调用它),人工填一次——这本身就是判定的一部分;
2. 或者对每条 **读它的调用者**(如 `contrib/run.py` 是否真的是入口),这正是第 28 轮说的"逐条人工判断";
3. 两者都要:J 只能覆盖**流水线脚本**这一层,覆盖不到"某个脚本被另一个脚本按名字调用"。
