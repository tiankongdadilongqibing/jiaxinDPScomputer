# 战斗编号、悬浮窗引用与 AI 精确选场实施规划

> 状态：待实施；本轮只制定方案，不修改插件行为。供主负责人派发任务。
> 目标：用户完成多场战斗后，能说“比较这几个编号”，AI 精确定位这些场次的导出，而不是猜测最新文件、文件排序或历史列表位置。
> 编号是定位能力，不替代比较准入、伤害口径和统计方法。

## 1. 推荐产品方案

采用“完整战斗引用 + 本次启动内短序号”双层展示。编号在新建统计会话时分配一次，导出、历史、日志、证据提取共用同一值。

拟定展示示例（示例值，不对应真实文件）：

```text
当前 #003   任务 411001   战斗中
战斗编号 B-20261005-143012-7A2C91EF-003   [复制引用]

上一场 #002   Lose   119.07s   已导出
战斗编号 B-20261005-143012-7A2C91EF-002   [复制引用]
```

- 短序号 #003 只用于同一次游戏启动内快速辨认，不能作为跨启动的唯一输入。
- 完整编号格式：B-{启动时UTC时间yyyyMMdd-HHmmss}-{随机32位十六进制令牌}-{会话序号至少3位}。时间用于阅读，不作为唯一性保证；超过999按完整数字扩展，不截断。
- 每次插件初始化生成新的启动命名空间；序号从1开始。随机令牌与时间相结合用于降低跨启动碰撞风险，但仍必须校验冲突，不能宣称数学上绝对唯一。
- 新命名空间若与已有索引/导出冲突，应重新生成；导入外部文件时发现同号异内容必须明确报冲突，不静默合并。
- 完整编号可放第二行，不因列宽挤压数值表；可以折叠详情，但复制按钮始终复制完整值。

**第一版不使用跨重启持久递增总计数器。** 它需要处理写盘中断、回滚、迁移和多进程争用，收益不足。完整编号已支持跨启动引用；若未来确需“历史第12345场”，另案实现人类别名。

## 3. 先冻结“一个编号是什么”

**第一版一个编号对应一个 BattleSession 统计会话，不承诺对应一整次关卡挑战。** 当前游戏可能按波次切多个会话；本需求不得顺手合并它们。

| 事件 | 编号行为 |
|---|---|
| 新建真实统计会话 | 分配新编号；允许空会话占号，缺号不表示数据丢失 |
| UI刷新、F5/F6/Chart切页、序列化 | 不分配、不改变编号 |
| idle软关闭后恢复同一会话 | 保持编号；暂存状态重新标为进行中 |
| 真正结束后再开下一场 | 新编号 |
| F9或Reset按钮 | 保留会话编号，增加 resetCount，显示“本场已重置”；不改变既有统计清除范围 |
| 旧历史被20条环淘汰 | 不影响磁盘导出的编号定位 |
| 游戏重启 | 新启动命名空间，短序号重新从1开始 |
| FromSummary等视图重建 | 复制原编号；没有原编号则明确legacy，不生成假新号 |
| 多段同一run | 每段有不同编号；保留原run.id/seq，离线按启动命名空间限定其作用域 |

F9 后的文件并不包含被清除的数据；索引和AI输入必须携带 resetCount。不得把“编号相同”解释为“整场完整”。不改变已有时间或伤害统计规则来迎合编号。

## 4. 身份字段与版本策略

建议在导出根对象新增独立 battleRef 块（拟定契约 battle-ref/1）：

```json
{
  "battleRef": {
    "schemaVersion": "1",
    "id": "B-20261005-143012-7A2C91EF-003",
    "launchId": "20261005-143012-7A2C91EF",
    "sequence": 3,
    "resetCount": 0,
    "revision": 1,
    "state": "final",
    "closeReason": "end"
  }
}
```

- id、launchId、sequence 创建后不可变；生成器隔离为可注入时间/随机源的可测试组件。
- revision 标识该会话内容快照修订，不能在 UI 每帧渲染时递增。重置、软恢复和之后内容变更必须使后续导出能区分；由统一快照协调器决定修订，不由每个writer各自++。
- 正常重复导出相同快照保持同revision；常规导出与证据副本共用身份和revision。快照内容不一致却同revision，应被校验器拒绝。
- state 至少区分 live / provisional / final；idle关闭为provisional，恢复为live。未知、无结果的关闭不得冒充已通关终局；closeReason保留实际原因。
- 保存成功/失败是写盘结果，不伪装成提前写入JSON的成功字段。UI/索引只在成功落盘后更新“已导出”。
- 新插件版本显式要求该块；旧版本缺块仍合法，按legacy处理。battleRef为元数据契约，不改 contribution 数学方法和既有贡献schema语义；若存在根导出schema版本则按兼容策略升级，同时升插件版本。
- 复制引用/分析清单绑定 id + revision + SHA256；id定位会话，hash定位实际文件内容。

## 5. 文件命名、写盘与索引

### 5.1 新文件默认命名

建议保留原前缀：

```text
battle_{quest}_{started:yyyyMMdd_HHmmss}__{完整id}.json
```

保留 battle_411001_… 兼容已有glob和quest位置。旧文件不重命名、不回填字段。新会话即使同任务同秒启动，也不能覆盖另一场。实际目标路径首次确定后绑定会话，后续不随系统时钟调整重新计算。

同一会话软恢复后的常规导出可以按现有方式更新同一目标文件，但必须更新revision；之前发给AI的固定清单不得静默跟随更新，需重新选择或使用已保存证据副本。证据目录中的历史材料不可覆盖。

### 5.2 最小可靠写盘协议

1. 从同一快照生成JSON，执行结构与身份校验；不合法不能标成功。
2. 写同目录临时文件，再通过适合当前平台的原子替换/创建完成发布；检查目标已有内容是否属于同一id。
3. 成功后计算实际字节SHA256，更新会话导出状态和可重建索引。
4. 写盘失败保留旧的完整文件、返回失败；新revision未成功时不得显示“最新数据已保存”。
5. 不在每帧渲染时扫描目录或写索引；不后台读取存活的IL2CPP对象。

这是导出边界的小型功能改动，单独提交并补失败注入测试，不能以重构名义忽略。

### 5.3 索引是缓存，不是真相

拟建 battle_catalog.json，放运行数据目录，不纳入Git。字段：id、revision、relativePath、hash、quest、started、duration、result、state、resetCount、pluginVersion。成功导出后按id更新，原子写盘。

- AI解析必须核对文件正文身份与hash；不能盲信索引。
- 索引缺失/损坏/滞后时允许从显式输入目录重建；报出无法读取项。
- 文件不存在则报missing，不把编号重新分配给另一文件。
- 同id不同revision：允许明确选择当前最高有效修订，输出选中修订；同id同revision异hash视为冲突。
- 同id同revision同hash的复制件可去重，但列明全部路径；不同来源库冲突不得自动猜。
- 第一批可先交离线扫描生成目录，再接运行时增量索引；最终最小版本必须能解析完整编号，不以索引UI存在代替链路完成。

## 6. 悬浮窗交互要求

所有页面的编号取自“正在展示的数据源”，而非统一读 Aggregator.Session。

| 位置 | 要求 |
|---|---|
| 主悬浮窗 | 常驻短序号，完整编号在第二行/详情；显示进行中/暂存/已导出/失败 |
| F5贡献表 | 标题绑定该场编号；数据不可用时仍显示明确场次身份，不回退到别场缓存 |
| F6明细、Chart | 绑定当前选择会话；时间线与编号同源 |
| 历史列表 | 每行编号、任务、结果、时长；历史第1行不是编号1 |
| IMGUI回退 | 至少文字展示完整编号；有能力时提供同一复制动作，不影响原热键 |

复制引用按钮可放在主窗/历史详情，第一版不要求所有表格行都加按钮；采用现有UI事件和GUI剪贴板接口，失败时显示可手动抄写的完整编号。快捷键只有确认无冲突后才可增加。

复制内容示例：

```text
DpsMeter battle-ref/1
battleId: B-20261005-143012-7A2C91EF-003
revision: 2
quest: 411001
state: final
resetCount: 0
file: battle_411001_20261005_143322__B-20261005-143012-7A2C91EF-003.json
sha256: <实际文件哈希>
```

进行中尚未导出时，只复制可得字段并明确“尚无可分析文件”，不能编造hash或文件存在性。编号本身不会上传数据，远程AI仍需要用户提供对应文件或证据包；本地AI可使用指定目录解析。

## 7. AI精确选场入口（必须交付）

拟建独立 battle_select.py；优先调用已有compare的 --files，不重写贡献算法。下列为拟定CLI，不是当前已存在命令：

```text
python battle_select.py list --exports <目录>
python battle_select.py resolve --exports <目录> --ids <完整编号A> <完整编号B> --out <selection.json>
python battle_select.py resolve --exports <目录> --launch <启动编号> --seq 3 5 8 --out <selection.json>
python battle_select.py compare --selection <selection.json> --out <报告目录>
```

selection.json 必须包含：用户原请求、解析目录、实际绝对路径、id/revision/hash、任务/时长/结果、state/resetCount、解析错误和选择顺序。执行比较前重新核验hash；文件已更新则停止并要求重新确认，不默认追踪最新值。

解析规则：

- 完整编号精确匹配，保留用户顺序；重复输入去重并提示，不把重复场计为两个独立样本。
- 短序号必须显式指定launch；用户只说“第3和第5场”且存在多个启动批次时，列候选并请求澄清，不能取最新。
- 任一个编号缺失/歧义/冲突，整组默认停止；不静默少比一场。
- live/provisional 默认只允许列出，不进入正式跨场比较；显式诊断模式必须标清未完成。final但resetCount>0需要额外完整性提示。
- 选择成功不等于可比较：仍运行既有任务、模式、装备、能力及身份准入；训练场与普通场不能因编号明确就混排。
- 所有子工具收到完整文件路径，不能再次通过glob、mtime或活目录猜输入。旧 --files 对不存在路径静默过滤的风险应在wrapper预检并在消费前复查。
- 保留现有compare的状态与退出码；选择层定义明确非零状态用于缺失、歧义、内容变化，不能以exit0加一句WARN代替拒绝。

用户可以直接发给AI：

> 请比较 B-20261005-143012-7A2C91EF-003 与 B-20261005-143012-7A2C91EF-005。先列出匹配的任务、时间、阵容和文件hash，确认无错场；再做比较准入与贡献分析，不补入其他场次。

## 8. 旧数据兼容

旧导出不改写、不补编号。离线列表为其生成 legacy:<完整SHA256> 引用，并显示原文件名与开始时间；这是文件引用，不是当时悬浮窗展示过的编号。可接受足够长的hash前缀，但必须在指定库内唯一，不唯一则拒绝。

新/旧导出都可以进入显式selection；能否合并比较交给既有准入。文件改名不影响正文id；旧文件以内容hash定位，同内容复制件去重，不按文件名计两场。

| 任务 | 负责人范围 | 交付与验收 |

**第一版完成范围**：完整编号、主窗/历史及各页身份一致、导出可定位、复制引用、离线精确多选、旧文件读取、失败拒绝和必要测试。
**后续可选**：历史多选按钮、直接复制多场提示词、自动打包证据、搜索过滤、永久累计别名。不得用可选功能拖延最小闭环。

## 10. 必须测试的场景

1. 连续两场、同任务同秒开始、系统时钟回拨、重启、序号超过999、随机源故意碰撞。
2. idle→resume→再次结束同号；真下一场新号；波次分段不同号但run关联保持；空会话不回收号码。
3. F9和Reset按钮同一重置入口保持id并更新resetCount；视图重建不发号。
4. A场有缓存、B场隐藏UI结束、打开历史：所有标题和复制内容指向B；关闭fold和异常路径也不得返回A编号或数字。
5. 同一数据的普通导出/显式证据导出同id/revision；内容不同同revision拒绝；软恢复后旧selection报hash变化。
6. 目录损坏、写盘失败、文件冲突、索引滞后/丢失、临时写入中断；旧完整导出不被破坏。
7. 历史超过20条仍可磁盘定位；改名、复制、旧版legacy、跨目录同号冲突、编号缺失/重复输入。
8. 两场/三场指定选择准确，compare只消费选择集合；其中一场缺失不得悄悄比较剩余场；训练场仍受准入限制。
9. 变异删除身份传播、改用History位置作号、ExportTo重新发号、将解析回退到最新文件、忽略hash检查，必须让具名测试失败且CLI非零。

测试不能只直接调用生成器：至少执行新会话→摘要→FromSummary→实际writer→解析器链路，UI测试取实际生产标题/复制模型。原生依赖在安全边界stub，不复制业务算法。

## 11. 发布与验收纪律

- 不改变 damage、DPS、贡献模型、KPI、波次合并、开关默认值或训练场资格；不修不删历史坏样本。
- 新增py登记tool_registry；新增md登记check_docs；运行数据索引、导出、selection含本机路径等派生产物放忽略目录，不误提交游戏资源。
- 测试用例数、变异数、验收命令数/检查数有变化时同步当前状态及索引，以当轮真实结果为准，不抄旧数字。
- 执行构建、行为测试、具名变异负控及全量验收；检验失败是否传播到最外层，未运行项必须披露。
- 各任务输出：修改清单、字段/接口、失败用例、命令/退出码、证据等级、已知限制、回滚方法；不得自行覆盖运行DLL。
- 需要实机目视时请求用户在正常游玩中顺带确认编号与复制，不要求为每个假设专门开战。
- 发布前关闭游戏、备份插件目录、核对前后hash及历史bak未变。回滚旧插件后仍保留新导出；解析器须继续能读新旧格式。

## 12. 最终用户验收

用户正常完成至少两场后，从悬浮窗抄写或复制编号，关闭并重启游戏后仍能通过原编号找到原文件；向AI提供多个编号时，AI先列出唯一对应的场次信息，再只对这些场次进行准入和分析。

**完成标准不是“屏幕上多了一个数字”，而是“这个数字能稳定、可审计地指向用户真正想比较的数据”。**
