# DpsMeter 1.7.11 之后的行为保持型重构方案

> 状态：建议方案，尚未实施。适用于主负责人分批部署给协作智能体。
> 依据：[入口索引](<D:/dmmplayer/rlyehshoujotaix_cl/DpsMeter-文档索引.md>)、[项目状态](<D:/dmmplayer/rlyehshoujotaix_cl/_dpsm_work/PROJECT-STATUS.md>)，并静态抽查生命周期、贡献缓存、工程文件和验收入口。
> 当前版本、32 份语料和 51 项验收成绩引用上述状态资料，本次不宣称重新跑过全量验收。已实际确认工作目录不属于 Git 仓库。
> 本方案编号 RF0–RF7，避免与状态文档的 R0–R4、已完成路线图的 N0–N7 混淆。

## 1. 结论：可以重构，但先修护栏，不先改机制

当前适合做小步、可回滚、保持输出语义的重构，不适合一次性重写。主要目标是：

1. 让生命周期、缓存、归属窗口能够离线执行测试。
2. 降低跨场状态污染及改一处牵动多处的风险。
3. 让代码边界与领域职责一致，而不只是减少单个文件的行数。
4. 保持既有贡献模型、伤害口径、比较契约、开关行为和历史兼容性。

**推荐主线：RF0 基线 → RF1 行为测试 → RF2 机械拆分 → RF3 纯逻辑抽离 → RF4 状态生命周期迁移。**

RF5 展示层、RF6 主数据适配器、RF7 离线工具整理在护栏就绪后独立推进，不要求一轮全部完成。第一轮只建议完成 RF0、RF1 和 RF2。

## 2. 对现有状态文档方案的校正

| 原方向 | 建议调整 | 理由 |
|---|---|---|
| Aggregator 拆 partial 是“无风险” | 改称低风险机械拆分；先补测试 | 文件拆分仍可能改变初始化顺序、漏编译或影响按路径扫描的守卫 |
| 先拆文件，再补纯函数测试 | 先钉住旧行为，再拆分，再提取 | 防止测试只证明新实现自洽 |
| 静态状态逐步挂到 BattleSession | 先分类生命周期，再决定归属 | 全局规则可提前登记下一场单位，不能每次结算一刀清空 |
| MasterData 合并与 crit 接线同批 | 分开；crit 接线属于功能研究 | 新观测值会改变数据语义，不是行为保持型重构 |
| 一次性脚本先打包归档 | 先依赖普查与只读目录索引；迁移和归档后置 | C# 参考实现与旧证据脚本可能仍被验收或复算引用 |
| 全绿且工具哈希零漂移 | 单次验收期间不得漂移；跨提交记录批准的变化 | 重构工具必然改变工具哈希，不能要求新旧哈希永远相同 |
| 历史导出重放证明插件重构正确 | 增加实际生产 C# 代码的执行测试 | 旧 JSON 重放能检验离线核心，不能证明新钩子或生命周期运行正确 |

文档小问题也应在 RF0 处理：状态表把 1.6.0 混入“无贡献段的段前版本”说明，与同文已知 1.6.0 坏样本相矛盾；命令段仍有 29/50，而顶部为 30/51；“最大的 6 个文件”列出 7 项。先从 manifest 和实际命令复算，再同步两份入口文档，不批量替换历史数字。

“不发生折叠丢步”仅说明该容量指标未超限，不能证明没有 CPU/分配问题；当前没有性能投诉或预算超标证据，因此不把实时性能改造纳入首轮。

## 3. 源码抽查暴露的重构约束

### 3.1 生命周期不能仅按 Start/End 二分

[Aggregator](<D:/dmmplayer/rlyehshoujotaix_cl/_dpsm_work/src/Aggregator.cs#L350-L432>) 启动时重置多类计数和探针，但部分计数明确按进程累计。

[软结束恢复](<D:/dmmplayer/rlyehshoujotaix_cl/_dpsm_work/src/Aggregator.cs#L459-L499>) 会取回旧会话、撤下旧历史摘要、恢复原生对象引用；其再次结算按现有逻辑覆盖同名导出。这是当前运行行为，重构不能擅改成禁止覆盖或永久只结算一次。工程人员不得手动改写历史证据，和游戏现有软关闭导出生命周期是两个不同约束。

[结算顺序](<D:/dmmplayer/rlyehshoujotaix_cl/_dpsm_work/src/Aggregator.cs#L651-L666>) 为探针/主数据读取 → 导出 → 清待配对列表 → 释放 Source → 刷新日志 → 记住关闭会话。提取函数时保留顺序、异常边界与读取时机。

[全局规则说明](<D:/dmmplayer/rlyehshoujotaix_cl/_dpsm_work/src/Aggregator.cs#L522-L527>) 明确禁止在结算清表：下一场单位已可能完成登记。它需要跨会话登记生命周期，不应直接塞进按局销毁的状态容器。

### 3.2 已有 C# 可执行测试，不是完全没有测试

[ReconProbe 工程](<D:/dmmplayer/rlyehshoujotaix_cl/_dpsm_work/recon_probe/ReconProbe.csproj>) 已直接编译生产 Contribution、AtkAddFold、CalcReconcile 等文件，无游戏依赖。缺的是规范化测试发现、分组与更广的生命周期覆盖，不应重写一套重复算法来“建立测试”。

[插件工程](<D:/dmmplayer/rlyehshoujotaix_cl/_dpsm_work/src/DpsMeter.csproj>) 是 net6.0，游戏引用硬编码绝对路径且 Private=false。先参数化 GameRoot 并保留当前默认路径，不能首轮升级框架、包版本或把游戏程序集复制进部署目录。

### 3.3 缓存行为需要先刻画，不能照注释重写

[ContributionSession.Get](<D:/dmmplayer/rlyehshoujotaix_cl/_dpsm_work/src/Output/ContributionSession.cs#L160-L227>) 的 stale 是“会话不同 OR 事件数改变 OR 开关改变 OR 时间超过一秒”。因此事件数变化可在一秒内再次触发计算；它不是严格的一秒节流。未处于战斗时则返回最近缓存，这不自动等同于完整的最终战斗结果。

以上是静态观察，不是实测性能缺陷。RF1 先测试现状；真正改节流、最终快照或历史选择行为时另列修复提交，重新定义预期、补负控和验收，不夹在文件搬迁里。

## 4. 目标架构：先逻辑分层，不急着增加部署程序集

建议边界（以下类名均为拟建名称）：

```text
Harmony Hooks / Unity callbacks
        ↓ 保持现有安全读取时机
Game adapters：原生对象访问、身份解析、主数据读取
        ↓ 有效值 + 缺失原因 + 必需的时间/身份信息
Battle coordinator：编排开始、事件、软关闭、恢复、结算
        ↓
Pure policies：时间窗、候选筛选、状态转换判据、数值构成
        ↓
Structured results / existing contribution core
        ├── Export adapter：既有 JSON 契约
        └── Presentation model → uGUI / IMGUI

Python：加载 → 校验/准入 → 比较 → 决策 → 报告
```

- 纯逻辑不得引用 Unity、IL2CPP、Plugin 静态配置、系统当前时间或磁盘 I/O。输入应为基元值或纯 DTO，时间与配置显式传入。
- 不为抽象而给每个类造接口；只对时钟、原生读取、导出/日志副作用和必要的 UI 输入建立测试边界。
- 第一阶段继续在现有插件程序集内编译；测试通过链接真实源文件执行。确有复用收益后再评估独立 Core 工程，避免先增加 DLL 装载风险。
- 保持 C# 与 Python 的独立数学实现，用交叉验证发现问题，不把两者生成成同一份算法而丢失独立性。
- 现有 Model 目录不自动等于纯领域层；每个文件按实际引用判断。

## 5. RF0：版本基线、资产边界和可复现验收（P0）

**交付**：本地版本管理方案、基线提交/标签、资产清单、独立验收目录、状态文档勘误。

1. 先确定仓库边界：建议纳入工作源码、测试、活跃工具、配置模板和当前文档；根目录入口文档也需跟踪。只做本地 Git，不设置远端、不上传。
2. 先写 ignore 与显式纳入清单，再检查 staged 文件；禁止对整套游戏无选择执行 git add。排除游戏资产/游戏 DLL、bin/obj、500MB 导出、运行日志、大型派生产物和备份。它们保留原地，以 SHA256 manifest 关联。
3. Git 不替代 DLL 回滚与语料快照；基线记录源码版本、部署 DLL、配置、测试工具、语料哈希和外部程序集依赖。
4. 验收输出进入每批独立目录。检查每个子命令是否真正遵守 out 参数；若仍写固定报告，先安排输出隔离，不覆盖已有验收档案。
5. 固定本批输入清单；新战斗文件另立新快照，不让批次执行中目录变动偷偷改变基线。
6. 修改文档数字前复算；检查现有 guard 是否只验证关键词存在，而没抓到命令计数和版本分布矛盾。

**验收**：可以恢复源码与工具到基线；产物和大资产不误入仓；旧 ERROR、RESTRICTED 等状态仍如实保留；未修改运行插件。

## 6. RF1：规范化 C# 行为测试与边界夹具（P0）

**顺序**：先迁入/复用现有 recon_probe 断言，再增加热点测试。保留旧探针入口作为兼容命令。

建议新增纯逻辑测试工程；优先 xUnit/NUnit 等已可用依赖，先检查本地包缓存与还原能力。若不可用，先采用现有无第三方依赖的可执行测试方式，输出用例名与非零失败码；不能为了测试先改变插件依赖。

### 必须覆盖的特征测试

| 范围 | 最小用例 |
|---|---|
| 时间窗归属 | 每个实际常量的边界前/等于/后；过期候选；多候选优先级；已消费不能再匹配；未知身份 |
| 时钟 | 同帧双驱动仅一次推进、暂停、帧停顿 clamp、game/real 分支、增量读取在判重之后 |
| 生命周期 | Start→Damage→End；idle→resume；真实 End 后迟到事件；restart；teardown；F9；连续 A/B 场 |
| 结算副作用 | 探针/导出/释放引用顺序；导出异常当前如何处理；软恢复再次结算合法而同一关闭重复触发如何处理 |
| 缓存 | 同会话新事件、同计数但 reset、新会话、useFolds 切换、无数据、结算后展示和历史选择 |
| 数学与序列化 | 已有手算用例、未知 owner、零分母、多 giver、精度往返、历史版本和已知坏样本 |

不能把原生对象在构造期不安全的 getter 改为提前读取来方便 DTO 测试。先测纯判据，再由薄适配器在原先安全时机提供输入。

**验收**：用临时副本变异窗口、候选顺序、Reset、开关或导出顺序时，至少对应测试会红；夹具执行生产代码，不只是复制生产公式；不能断言“测试数上升即覆盖充分”。

## 7. RF2：Aggregator 机械拆分（P1，第一轮上限）

**依赖**：RF0/RF1。唯一修改负责人，不与生命周期逻辑抽取同时进行。

建议将[Aggregator](<D:/dmmplayer/rlyehshoujotaix_cl/_dpsm_work/src/Aggregator.cs>) 分为以下拟建 partial：

- Aggregator.cs：公共门面及集中静态字段初始化。
- Aggregator.Session.cs：开始/结束/软恢复/run 标记。
- Aggregator.Clock.cs：Tick、FrameDelta、采样时机。
- Aggregator.Attribution.cs：候选记录、配对与来源解析。
- Aggregator.Stats.cs：伤害/治疗记录及累计。
- Aggregator.Finalize.cs：摘要、日志、探针和导出编排。

首个提交只移动方法，保留访问级别、签名、调用次序、异常范围、集合与线程语义。相互依赖的静态字段初始化留同一文件，不依赖 partial 文件顺序。命名常量提取另一个提交，保持值、单位和比较符号，不把不同用途但数值相同的窗口强行合并。

路径解析型 guard 在旧位置运行时先确认能拒绝负例，再调整扫描新文件；不能删掉断言让搬迁通过。

**出口**：构建与探针通过、机械差异审查、生产逻辑夹具输出相同、全量验收预期相同。此批只是可维护性改善，不声称已降低运行耦合。无需为每个 partial 要求单独实战；可暂不部署。

## 8. RF3：纯判据下沉与协调器边界（P1）

**优先抽取**：归属候选过滤/排序、时间窗判断、run 归组判据、时钟增量策略；先小函数，后状态机。

拟建 AttributionPolicy、BattleClockPolicy、SessionTransitionPolicy，输入显式时间、候选列表和标志，输出选择结果及理由；所有原生读取、对象存活检查、日志和导出仍由旧门面负责。

- 不改变候选遍历顺序、同分处理、Used 标记时机、退化路径和拒绝条件。
- 不顺手把 DateTime 全换 Stopwatch；时钟来源及时间单位变更是行为修复。
- 不重新排列 fold/cancel、浮点乘法/加法与取整；数学交换律不保证浮点逐位一致。
- 不把 JudgeClause 拆成显示与计算两套裁决。

**出口**：同夹具旧/新函数结果、理由码和副作用序列一致；真实导出继续作为数值回归，而不是原生调用正确性的唯一证据。

## 9. RF4：按生命周期迁移可变状态（P1，高风险，后置）

先交付 StateLifetimeMatrix，逐字段说明 owner、创建、重置、软恢复、最终释放、被谁读取。

| 生命周期 | 应包含的状态 | 迁移约束 |
|---|---|---|
| 单击/攻击快照 | 状态、耐久、构成上下文 | 攻击开始采样与 finally 清理保持 |
| 单场运行态 | 配对队列、当场计数、时钟游标 | 同步考虑 reset、soft close、resume，不只 Start/End |
| 跨场衔接 | 最近关闭会话、run 标记、预登记全局规则 | 不按 End 一次性清空；分别定义所有权 |
| 进程级 | 稳定主数据、明确累计计数、历史容器 | 不强行挂在每场对象上 |
| 展示级 | 当前视图、缓存、筛选状态 | 不反向改变统计模型 |

建议保留 Aggregator 静态门面作为兼容壳，逐个状态族迁到 BattleRuntimeState/SessionCoordinator，而不是一轮消灭全部 static。纯模型不得因此获得 Unity/IL2CPP 依赖。

历史快照不可变化是理想方向，但当前软关闭会话可恢复；必须区分“暂存摘要”和“最终摘要”，本轮先保持现状，确需改快照语义时另立 ADR/修复，不悄悄深拷贝。

**出口**：A/B 多场、软恢复、F9、销毁/重建及下一场提前登记的执行测试；正常游玩时合并一次运行验证。发现跨场差异立即回滚该状态族，不与数学修复一起排查。

## 10. RF5：展示模型与统一格式化（P1/P2）

从[贡献输入与缓存桥接层](<D:/dmmplayer/rlyehshoujotaix_cl/_dpsm_work/src/Output/ContributionSession.cs>)分离输入投影、计算调用、缓存策略、视图选择；保持一个 Contribution.Compute 核心。

表格建议拆为 ColumnSpec / RowViewModel / DisplayFormatter / renderer：列定义与格式化有单一生产来源，uGUI/IMGUI 消费同一视图，不各算一套贡献。测量字体与 Unity 绘制留在适配器。

独立布局守卫不能仅导入同一列定义再断言自身等于自身；保留固定期望输出、长名/CJK/极值/零/未知用例，并执行实际生产格式化。

缓存修复分支若决定采用严格节流，应写清事件变动、强制刷新、结算、F9和配置变动的规则；不能以静态 OR 改 AND 后“看起来更快”作为完成。

**出口**：两渲染器使用相同数据口径；旧布局可接受样本不漂移；目视仅验证正常游玩中可确认项，未覆盖的字体环境仍标待验收。

## 11. RF6：主数据适配器与导出边界（P2）

主数据查找的“两处重复”目前是状态资料中的线索，执行者先定位调用方并读全上下文，再提取 MasterDataAccess。必须保持：非泛型集合路径、对象判空差异、解密读取、字段布局验证、失败计数、加载失败后重试及原生对象存活策略。

导出可以按段拆 writer，但先不更换 JSON 库、不改字段顺序/精度/省略规则、不异步化原生访问。保留写盘前 JsonCheck，UI 与导出共用计算而非各自推导指标。

**验收**：缺表/延迟加载/读取失败区分；所有真实文件 schema 与贡献交叉验证保持；新增真实运行读取路径须正常游玩验证。暴击观测接线完全另案。

## 12. RF7：离线工具包与文档治理（P2）

先写工具注册表，标明活跃 CLI、导入关系、输出副作用、预期退出码、输入版本和历史证据。再逐批迁移到 tools/、tests/、research/ 等拟建目录，旧脚本保留薄入口兼容；不要一轮移动全部文件。

可共用路径解析、manifest、输出目录、JSON I/O 和运行证据结构，但保留 ComparisonEligibility、compare、decision、budget 的契约边界，不将不同状态词表硬揉成一个。CLI 工作目录和退出码都属于兼容面。

archive 的前置：证明没有活跃调用；记录清单与哈希；打包后验证可读取并回环核对。当前只需索引，不删除或移动任何历史证据。C# 参考实现尤其不能仅因在 src 外就当废弃物。

**验收**：旧命令与新入口产生等价结果，批量预期 ERROR 不被吞；每条入口至少一条端到端负控。文档只保留一个现状事实入口，历史报告不改写。

## 13. 行为等价与验收矩阵

| 层次 | 验收方法 | 不能替代什么 |
|---|---|---|
| 纯机械移动 | 构建、差异审查、实际生产代码测试 | 不自动证明 native 生命周期正确 |
| 纯函数提取 | 边界夹具旧新对照、临时变异负控 | 不能只断言自洽 |
| 数值/导出 | 同输入完整结果与 schema 比对、既有 C#/Python crosscheck | 不等于每条钩子都运行过 |
| 状态迁移 | 序列测试、副作用顺序、跨场测试 | 不只看单场总量 |
| UI | 生产格式化执行、独立布局守卫、目视 | 文本日志不能证明字体没遮挡 |
| 工具迁移 | 旧/新 CLI、退出码、异常路径和输出目录 | exit 0 不等于所有项目 PASS |

等价标准提前定义：整数、键、事件顺序和拒绝理由应精确一致；浮点保持既有序列化与容差，不为重构放宽；允许变化的版本/生成时间等元数据逐项白名单，不能用“大量忽略字段”隐藏漂移。构建产物哈希可能因源码/PDB 改变，行为等价不要求 DLL 与旧版哈希相同；发布包与部署 DLL 必须相同。

批次最终运行完整 n0_acceptance；开发中可使用局部测试，但 quick/skip-heavy 必须标为未全验收。源码改变后即使全部旧导出重放通过，也必须通过新产物生产逻辑执行测试。

## 14. 协作、发布与回滚

- 主负责人独占版本/部署/共享契约/验收基线；每个批次一个主要改动层，一个小提交解决一个目的。
- RF0 基线建立后，RF1 测试设计、RF5 只读设计、RF7 依赖普查可并行；Aggregator 的 RF2/RF3/RF4 必须串行。
- 每次拆分保留旧公共门面，下一批再减少依赖；不同时修改 Hook ABI、数学公式、文件路径与 UI。
- 每批交付：文件清单、调用图/状态矩阵、变更前后输出、运行命令和退出码、未运行项、回滚标签、实际产物哈希。
- 开发提交不必每次部署；正式插件发布按项目规则升版本，纯结构变化不擅升 schema/method。
- 发布前保留上一版源码标签+插件+配置证据；运行中不替换被加载 DLL。回滚同时匹配源码与工具，不能只复制 DLL 后宣称整个工作区恢复。
- 任何新伤害差异、历史错位、早期规则漏登记、开关失效、未知异常退出都暂停该批。保留失败证据，不修旧样本或扩大容差。

## 15. 首轮完成定义与不做事项

**首轮完成**：本地基线可恢复；测试执行真实生产代码；时间窗/缓存/生命周期至少有最小负控；Aggregator 机械拆分完成且行为不变；全量验收状态符合预期；没有要求用户为每个文件各打一场。

**本轮明确不做**：改变 dealt/吸收口径、改变会话合并规则、接入新暴击观测、增加配队页、调整归因模型、重写整个 CompositionProbe、升级 Unity/.NET/Interop、引入事件总线或通用 DI 框架、删除历史证据。

下一轮是否推进 RF4 应由 RF1/RF3 的覆盖程度决定，而不是由“已经拆成多少文件”决定。重构成功的标准是：同样的数据与行为更容易验证、修改和回滚，而不是目录更漂亮。
