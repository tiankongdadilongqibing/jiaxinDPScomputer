## 1. 现状:可执行的事实

### 1.1 调用图(实测,不是推测)

| 消费者 | 路径 | 用不用缓存 |
|---|---|---|
| 实时面板 | `OverlayUGUI.Rows.ResolveContributionView` → `ContributionSession.Get(useFolds)` | **用**(活分支) |
| "上一场"视图 | 同一个 `ResolveContributionView`:拿 `Get` 的结果,但**非活分支**只要 `Aggregator.History` 非空就用 `History[0].Session` **重算**并按摘要备忘 | 只作回退 |
| 导出 | `ExportService` → `ContributionSession.AppendJson` → `Compute` | **完全不用** |

`ContributionSession.Get` 在生产里只有 **1 个调用者**;`ContributionSession.Invalidate()` 在生产里**没有任何调用者**
(唯一的提及是一处注释,另有测试调用它)。

### 1.2 规则(已抽成纯判据,行为不变)

```
stale = !ReferenceEquals(缓存会话, 当前会话)
     || 缓存事件数 != 当前事件数
     || 缓存用折叠 != 本次用折叠
     || now - 缓存时刻 > 1.0            // 严格大于
```
- 前两条读取活分支前置检查:活分支在 `useFolds == false` 或**事件数为 0** 时提前返回不可用,根本走不到这里;
- 缓存初值:事件数 `-1`、时刻 `-1e9` ⇒ 第一次调用必然重算。

### 1.3 两条与直觉相反的既有事实(RF5 调查找出来的)

1. **它不是节流。** 源码注释写的是 "refreshed at most once a second, and only when the event count actually moved",
   但四个条件是 **OR**:事件计数一变就**立刻**重算,一秒上限只在计数不变时才起作用。
   所以"至多一秒一次"**不成立**;真实语义是"计数一变就重算,另有 1 秒最长复用期"。
   代价层面这没问题(一次 `Compute` 约 3 万次运算,亚毫秒),问题在**注释失实**与后续决策的措辞。
2. **`_cacheUsedFolds != useFolds` 这一支从门面不可达。** 用折叠开关为假时 `Get` 提前返回不可用视图;
   而缓存里的该标记只会被写成真。它保留着(删它是行为决策,不是重构),并由用例同时钉住"若被走到则成立"与
"门面走不到"。

## 2. 被用例钉住的危险行为(改动前必须先改预期)

| 用例 | 行为 | 风险 |
|---|---|---|
| `cache/same-session-refilled-to-the-same-count-returns-the-OLD-cache` | 同一会话被重置并**在 1 s 内回填到相同事件数**时,复用旧缓存 | 面板可能显示旧数字;超过 1 s 或计数不同则自动恢复 |
| `cache/the-stale-cache-still-reports-the-live-clock` | 复用缓存时用的是**当前**会话的时钟与任务号,不是缓存的 | 数字与时钟不同源,视觉上像"表没更新" |

## 3. "暂存摘要 vs 最终摘要"的现状

方案要求区分两者。**这一分离已经存在,只是在展示层而不是在 `ContributionSession` 里**:
`ResolveContributionView` 在"上一场"场景下**重算** `History[0].Session`(即 `ExportService` 写贡献段用的**同一个对象**),
并按摘要对象 + 折叠开关备忘(`_prevSummary` / `_prevSummaryView` / `_prevSummaryUsedFolds` 三个字段)。
源码注释记录了要做到这一步的原因:缓存只在活分支刷新,而 F8 隐藏或停在明细/图表页时**根本不刷新**,
于是 F5 会显示再上一场;而"结算时 `Invalidate()`"不是解法 —— 那个缓存同时是唯一持有已结束战斗结果的地方。

因此 `Get` 的非活分支(返回缓存)实际只是**回退**:`History` 为空(刚启动、或历史被清)或重算抛异常时才生效。

## 4. 选项

| 选项 | 内容 | 用户可见后果 | 代价 |
|---|---|---|---|
| **A 保持现状 + 修文档**(本轮结论) | 只把注释与文档改成真实语义("计数一变即重算,另有 1 s 最长复用期") | 无 | 零;危险行为仍按 §2 记录在案 |
| B 严格节流 | 1 s 内即使计数变化也不重算 | 面板最多滞后 1 s(打点密集时更平滑) | 需定义"结算/F9/配置变更"是否强制刷新,否则收尾数字会滞后 |
| C 事件驱动 + 强制刷新点 | 去掉时间条件,改为"计数变化 or 强制刷新" | 面板最准 | 每击一次重算;必须逐一命名强制刷新点(结算、F9、配置变更、视图切换) |
| D 暂存/最终分离写进契约 | `Get` 的非活分支不再回退到"恰好持有的缓存",改为"暂无战斗数据";历史一律由展示层从 `History[0]` 重算 | 极少数边界(历史为空)从"显示上一次的表"变成"暂无" | 与现有用例冲突,需改预期;换来的是**缓存只描述它真正刷新的那一场** |

## 5. 需要决策的三个问题

| # | 问题 | 我的建议 | 理由 |
|---|---|---|---|
| Q1 | 面板允许"事件计数变化后"最多滞后多久? | **0(即现状 A)** | 现在亚毫秒级,收益是准确;真正的节流需求应由实测帧耗时驱动,而不是照抄"至多一秒"的说法 |
| Q2 | `F9`(重置当局)是否应调用 `ContributionSession.Invalidate()`? | **应该**(一行改动 + 一条用例) | 它把生产中唯一没有调用者的公共 API 接上,并直接消除 §2 第一条危险行为;结算时不能调用(注释已论证),但**重置**时缓存描述的数据正要被丢弃 |
| Q3 | 历史分支在 `History` 为空且缓存存在时,继续返回缓存(现状)还是明确"暂无"? | **先保持现状**,与 Q2 一起评估 | 现状由展示层重算兜底,边界收益小;若采用 D 再一起改 |

## 6. 本轮**没有**改的东西(以及为什么)

- 没有改 `Get` 的判据语义(只把它搬进 `Policy/ContributionCachePolicy`):方案 §15 把缓存语义变更列为**需决策**,
  而 §14 要求"行为改变必须同时给出旧行为、新行为、证据与回滚";
- 没有给 `F9` 接上 `Invalidate()`(Q2 待决):它是一个行为改动,虽然只有一行,但会改变 §2 第一条被钉住的行为;
- 没有动 `_prevSummary*` 备忘(它是展示层状态,且当前行为有注释与用例解释)。
