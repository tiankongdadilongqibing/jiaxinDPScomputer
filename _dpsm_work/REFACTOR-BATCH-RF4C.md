## 1. 迁移了什么

| 迁移前 | 迁移后 |
|---|---|
| `CompositionProbe` 的两个静态字典:`Dictionary<long, List<GlobalRule>> _globalRules` 与 `Dictionary<long, string> _ruleOwnerName` | 一个 `GlobalRuleRegistry<GlobalRule>` 实例(两个字典都在它里面) |
| 19 处直接读写(`ClearGlobalRules` 的遍历 + 逐元素 `try/catch`、跳过判定的 memo 查询、阀门的两个阈值判断与整表清空、应用路径的 `foreach` 与 `Count`、登记时的两条赋值) | 容器的 `TryGet` / `HasOwnerName` / `OwnerNameOf` / `Set` / `Reclaim` / `ClearAll` / `Count` / 枚举 |

**为什么是泛型容器**:规则类型 `GlobalRule` 持有 `BattleObject`(IL2CPP),所以容器不能在离线测试里编译。
把它做成 `GlobalRuleRegistry<TRule>`、把"存活判定"作为 `Func<TRule,bool>` 传入,容器就与游戏无关,
而探针传入的判定就是那条原生读取(`GameRef.IsNull(r.OwnerObj)`,自带 `try/catch`)。

## 2. 容器负责的三条性质(每条都有用例)

1. **战斗结算不会清表**:容器没有任何"结算/开始"入口;唯一的删除路径是 `Reclaim` 与 `ClearAll`(阀门调用)。
   用例 `a-finalisation-does-not-drop-the-next-battles-registration` 把这句话变成可执行:登记下一场的单位 →
   (模拟结算,不触碰容器)→ 回收 → 条目仍在、规则仍可读、名字备忘仍能阻止重扫。
2. **只回收死掉的持有者**:`Reclaim(predicate)` 返回丢弃条数;活着的持有者连同它的规则一起留下。
   这条正是源码注释里记录的缺陷(整表清空让一个全体增益消失到持有者下次行动;实测 ミャウラ 的
   `+15%` 在 01:29:53.111 被清、01:29:53.215 才回来,[賢導]トレイラ 的开场命中读成 ×1.491 而不是 ×1.714)。
   **空条目永远丢弃**(它是"扫过、没找到"的备忘),所以活着的单位会被**恰好**重扫一次 —— 也有用例。
3. **枚举顺序 = 插入顺序**:应用路径在这个顺序上连乘 double,而浮点乘法**不满足结合律** ——
   方案明确禁止重排。容器沿用同一个 `Dictionary` 与同一套增删顺序,并有一条用例把"插入序"与
   "回收后幸存者保持相对序"钉下来:将来运行库若改变枚举顺序,红灯会告诉我们"浮点乘积的顺序变了",
   而不是让它在导出差值里悄悄出现。

## 3. 行为保持

| 手段 | 说明 |
|---|---|
| 同一容器类型、同一增删顺序 | 顺序敏感(见上),所以没有换集合、没有排序、没有延迟删除 |
| 死键先收集后删除 | 保留原来的"先收集再删"写法:边遍历边删是未定义行为,且**删除顺序**会影响字典的空闲表,进而影响之后的枚举顺序 |
| 逐元素 `try/catch` 语义 | 移到探针的 `OwnerAlive` 谓词里:原生读取抛异常仍算"已消失",循环继续 —— 与原来一致 |
| 两条赋值保持原顺序 | `Set` 内部先写规则、再写名字备忘(与迁移前的两行一致) |
| 登记"即使为空也写入" | `Set` 的文档与用例都写明空列表是"扫过"备忘 |

## 4. 未做 / 下一步

1. **`ApplyGlobalDebuffs`(应用侧)未动**:它读 `_curHitType`、受害者状态、位置/属性门,并以 `FoldContext` 为输出;
   属同一族的另一半,需要先把"命中事实"投影出来才能离线测(与 RF3 里"候选扫描留在门面"是同一个理由)。
2. **注册路径本身仍未离线驱动**:本轮证明的是"注册表在结算前后如何存活/回收",不是"注册扫描能从原生对象里读出什么"
   (后者已在 RF4b 用纯分类器覆盖了判据部分,原生读取部分仍靠实机与真实导出回归)。
3. **`ClearGlobalRules` 的调用点**只有阀门一处:容器没有把"何时回收"也收进去(那是策略),保持现状。
